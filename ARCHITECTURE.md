# Архитектура обработки

```text
 генератор ──(идемпотентный продюсер)──► telemetry.v1   [1 партиция = 1 площадка, ключ unit_uuid]
                                              │  read_committed, группа vqueue-processor-<site>
                                              ▼
                        ┌──────────── процессор площадки ────────────┐
                        │ decode → SiteState.apply (домен, без IO)   │
                        │ одна транзакция на батч ≤ 500 сообщений:   │
                        │   выходы + снимок с позицией + офсеты      │
                        └─────┬───────────────┬───────────────┬──────┘
                              ▼               ▼               ▼
                         decision.v1      queue.v1      vqueue.state.v1
                         4 партиции       4 партиции    1 партиция, compact
                         ключ unit_uuid   ключ station  ключ site_id
```

## 1. Сколько процессоров и по какому критерию

**Один процессор.** Критерий: *отдельный процессор выделяется на каждую группу данных, которые должны меняться атомарно и согласованно на каждом сообщении.* Для площадки такая группа одна: занятие станций, очереди всех станций, перенаправления и решения зависят друг от друга на каждом сообщении.

Рассмотренные и отвергнутые варианты:

| Вариант | Почему отвергнут |
|---|---|
| B: unit-processor (по машине: дубли, фазы) + site-processor (очереди, решения) | Граница консистентности не меняется: site-processor всё равно один на площадку, а между процессорами появляются промежуточный топик, вторая транзакция и задержка. Выигрыш — разгрузка CPU, которая при 40 сообщениях/с не нужна (п. 4, п. 7) |
| C: unit / station / decision | Цикл: решение меняет очередь (перенаправленная машина переходит в очередь другой станции), а решению нужны очереди всех станций. decision → queue → decision через топики — обратная связь с задержкой, своё «сейчас» у каждого процессора и потеря детерминизма: результат зависит от того, какой процессор раньше дочитал свой вход |

## 2. Ключ и состояние

- **Вход** `telemetry.v1` — ключ `unit_uuid`, как в ТЗ. **Процессор работает на площадке**: экземпляр владеет единственной партицией входа (одной площадкой, `SITE_ID`), ключ его состояния — `site_id`. Если назначено больше одной партиции, `KafkaRunner.on_assign` завершает процесс с ошибкой.
- **Состояние** — `SiteSnapshot` (`src/vqueue/domain/site.py`):
  - «сейчас» — наибольший учтённый `ts` площадки;
  - треки машин: последний учтённый `ts` (фильтр дублей), позиция, фаза и станция, вход в радиус станции (станция и момент), признак нахождения в радиусе разгрузки;
  - занятость станций: последняя занявшая машина с моментами занятия и освобождения, обслуженные визиты (чтобы не занимать повторно);
  - действующие перенаправления (машина → рекомендованная станция);
  - машины, получившие решение в текущем заезде;
  - последние опубликованные очереди (публикация только при изменении).
- **Размер**: 10,7 КБ JSON на 40 машин и 4 станции после часа симуляции; кодирование 0,13 мс, разбор 0,09 мс. Снимок пишется целиком один раз на батч (до 500 сообщений), а не на сообщение; в заголовке записи — позиция чтения `telemetry.v1` (`telemetry-next-offset`, п. 5).

## 3. Машины, станции и «все станции сразу»

Конфликт ключей (вход по машине, очередь по станции, рекомендация по всем станциям) снят выбором **площадки как единицы консистентности**: всё состояние площадки в одном процессе, и `apply` одного сообщения последовательно обновляет трек → занятость → очереди всех станций → решение → очереди с учётом решения. Решение видит очереди, согласованные с тем же сообщением.

Порядок важен не только внутри машины: какая из двух машин займёт освободившуюся станцию, решает порядок их сообщений. Поэтому у площадки **одна партиция `telemetry.v1`** — единый порядок сообщений, и повторный прогон того же топика даёт те же выходы. «Сейчас» — глобальный максимум `ts` площадки; часы компьютера в расчёт не попадают (`at` в выходах — тоже время событий).

## 4. Партиции, реплики, параллелизм

| Топик | Партиций | Ключ | Почему |
|---|---|---|---|
| `telemetry.v1` | 1 | `unit_uuid` | одна площадка, единый порядок → детерминизм |
| `queue.v1` | 4 | `station_uuid` | параллелизм потребителей; порядок по станции сохраняется |
| `decision.v1` | 4 | `unit_uuid` | то же, порядок по машине |
| `vqueue.state.v1` | 1, `compact`, `segment.ms=600000`, `min.cleanable.dirty.ratio=0.1` | `site_id` | последний снимок площадки; короткий сегмент — чтобы восстановление не перечитывало старые снимки |

**Реплики.** Активная — одна на площадку (одна партиция в группе); резервные экземпляры с **другим** `INSTANCE_ID` в той же группе ждут rebalance. При падении активного резервный получает партицию через `session.timeout.ms` (45 с по умолчанию) при любом членстве. Разница — при штатной остановке: динамический участник выходит из группы сразу, статический (явный `INSTANCE_ID`, как на стенде) — нет, и резервный снова ждёт `session.timeout.ms`. Зато перезапущенный статический участник с тем же id получает свою партицию сразу, без rebalance.

**Параллелизм** ограничен числом площадок: внутри площадки обработка последовательная. Сейчас вход — один топик `telemetry.v1` с одной партицией для одной площадки; вторая площадка — отдельный входной поток и отдельный экземпляр со своими `SITE_ID`, группой и конфигурацией. Модель «площадка = партиция общего топика» потребует `assign()` по сопоставлению `SITE_ID` → партиция вместо `subscribe()` — не реализовано.

**Запас.** Замер на Apple M1 Pro, Python 3.11: час симуляции рабочей площадки (40 машин, 2 % дублей, 2 % опозданий) — 146 790 сообщений. `SiteState.apply` — 83 мкс на сообщение (~12 000 сообщений/с); с разбором JSON, кодированием выходов и снимком на каждые 500 сообщений (`TelemetryProcessor.process`) — 92 мкс (~10 900 сообщений/с). Брокер в замер не входит. Поток площадки по ТЗ — 40 сообщений/с, запас по CPU ~270×; догон: минута простоя площадки (~2 400 сообщений) обрабатывается за ~0,25 с. Методика: `Simulation` + `FaultInjector` (seed 11) → `encode_telemetry` → время прохода по `time.perf_counter`, лучшее из трёх прогонов.

## 5. Гарантии доставки

- **Транзакционность — на выходе процессора.** Батч фиксируется одной транзакцией Kafka: записи `decision.v1` и `queue.v1`, снимок в `vqueue.state.v1` с позицией чтения в заголовке и офсеты группы `telemetry.v1` (`send_offsets_to_transaction`). Потребители выходов должны читать с `isolation.level=read_committed`. Выходы, состояние и позиция чтения не могут разойтись: состояние и позиция — одна запись, и она фиксируется вместе с выходами.
- **Почему позиция в снимке, а не только в офсетах группы.** Новый владелец партиции читает топик снимков до LSO, а офсеты группы librdkafka запрашивает отдельно (с `require_stable`, дожидаясь незавершённой транзакции). Если транзакция «зомби» зафиксируется после чтения снимка, но до чтения офсетов, позиция окажется «после батча», а состояние — «до», и батч выпадет. Поэтому `on_assign` берёт позицию из заголовка того же снимка (`consumer.assign` с офсетом). Офсеты группы по-прежнему коммитятся в транзакции — для мониторинга лага и как запасной вариант, если снимка или заголовка нет.
- **Переход на резерв посреди транзакции «зомби».** Снимок читается не до LSO, а до настоящего high watermark: его запрашивает отдельный клиент с `read_uncommitted` (librdkafka запрашивает watermark с уровнем изоляции клиента, и read_committed-клиент получил бы LSO). Если у прежнего владельца транзакция открыта, восстановление ждёт её исхода — не дольше `transaction.timeout.ms` = 20 с; предел восстановления — 60 с. Чтобы снимок «зомби» гарантированно оказался ниже этого watermark, записи батча доставляются (`flush`) до `send_offsets_to_transaction`: раз брокер принял офсеты со старым поколением группы, снимок уже в топике, а новый владелец запрашивает watermark только после rebalance.
- **Идемпотентности достаточно**:
  - на входе — генератор пишет идемпотентным продюсером, а дубли и переупорядочивание всё равно отсекаются правилом `ts` в домене; транзакции на стороне генератора не нужны;
  - для `queue.v1` — это состояние по ключу станции: повторная публикация той же очереди безвредна, потребителю достаточно последнего значения по ключу;
  - для `decision.v1` при полном перепроигрывании — см. п. 6.
- **Ошибки** (`src/vqueue/adapters/kafka_runner.py`): abortable (`txn_requires_abort`) → `abort_transaction`, откат состояния процессора к снимку начала батча, `seek` к началу батча и повтор (после 5 откатов подряд — падение); retriable в `send_offsets_to_transaction` / `commit_transaction` → повтор того же вызова до 3 раз; abort тоже повторяется при retriable-ошибке; любая иная ошибка внутри транзакции (например, `BufferError` переполненной очереди продюсера) — abort и падение, чтобы незакрытая транзакция не держала LSO выходных топиков; fatal → процесс падает, перезапуск восстанавливает состояние (п. 6). Нефатальные ошибки консьюмера librdkafka исправляет сам — они пропускаются с предупреждением. Некорректное входное сообщение пропускается с предупреждением в логе.
- **Fencing.** `transactional.id = vqueue-processor-<SITE_ID>-<INSTANCE_ID>` — у каждого экземпляра свой; перезапуск с тем же id в `init_transactions` фенсит прежний и закрывает его незавершённую транзакцию. «Зомби» после rebalance отсекается по поколению группы: метаданные группы передаются в `send_offsets_to_transaction` (KIP-447), и брокер отклоняет офсеты устаревшего владельца. Транзакцию, офсеты которой приняты ещё до rebalance, поколение не отсекает — её дожидается восстановление снимка (см. выше).

## 6. Рестарт

- **Откуда состояние.** При назначении партиции процессор читает `vqueue.state.v1` (read_committed) до high watermark, берёт последний снимок по `site_id` и позицию из его заголовка; `telemetry.v1` читается с этой позиции. Детерминизм восстановления проверяется property-тестом (восстановление из снимка в любой точке потока даёт те же выходы, что и непрерывная обработка), совпадение позиции в снимке с офсетом группы — интеграционным тестом.
- **Сколько времени.** Читается весь топик снимков: после компакции — последний снимок плюс снимки активного сегмента, который компакция не трогает (не старше `segment.ms` = 10 мин). Снимок ~11 КБ пишется раз на батч — примерно раз в 1–1,25 с (батч до 500 сообщений или 1 с ожидания); это до ~500–600 снимков, ~5,5–6,6 МБ. Затем вход в группу; с тем же статическим `INSTANCE_ID` — без rebalance. Интеграционный тест `test_exactly_once.py`: в замеренном прогоне SIGKILL пришёлся на офсет 2 500 из 31 495 (тест требует ≥ 1 000); перезапуск с тем же `INSTANCE_ID` дообработал остаток ~29 тыс. сообщений за ~6 с, включая старт процесса и восстановление; выходы совпали с эталоном без дублей и потерь.
- **Уже выданные решения при обычном рестарте** не дублируются: незафиксированная транзакция отменена, read_committed-потребители её не видят, обработка продолжается с позиции, записанной в том же снимке.
- **Полное перепроигрывание с нуля.** Пустое состояние и чтение с начала: новые `CONSUMER_GROUP` и `SITE_ID`; либо при остановленном процессоре — tombstone снимка (ключ `site_id`) **и** `kafka-consumer-groups.sh --reset-offsets --to-earliest` для группы. Один tombstone без сброса офсетов даст пустое состояние с середины топика. Решения и очереди будут опубликованы повторно и — при той же `config/site.toml` и той же версии кода — **идентичны** прежним, включая `at`: порядок входа единый, время — время событий. Потребителю `decision.v1` достаточно идемпотентности по `(unit_uuid, at)`: решение принимается не чаще раза за заезд. Час телеметрии площадки перепроигрывается за ~13,5 с CPU (п. 4) плюс чтение из брокера; retention `telemetry.v1` должен покрывать нужный период.

## 7. Что сознательно не вынесено в отдельный процессор

- **Приём** (дедупликация, фазы машины). Он ключуется по машине, и граница в коде уже есть: `domain/ingest.py` и `domain/unit_fsm.py` не зависят от состояния станций (занятости, очередей) — только от их координат в конфигурации. Вынос — путь эволюции при упоре в CPU; сейчас это добавило бы промежуточный топик и вторую транзакцию при запасе ~270×, а порядок сообщений разных машин площадки всё равно пришлось бы сохранять для занятия станций.
- **Рекомендация отдельно от очереди** — нельзя: решение меняет очереди (перенаправление), а очереди нужны решению; разделение даёт цикл через топики (п. 1, вариант C).
- **Публикация и сериализация** — адаптер того же процесса (`adapters/codec.py`, `adapters/processor.py`, `adapters/kafka_runner.py`): отдельный процессор публикации разорвал бы транзакцию «выходы + снимок + офсеты».
