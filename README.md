# vqueue — виртуальные очереди

Сервис читает телеметрию машин из Kafka (`telemetry.v1`), восстанавливает по ней очереди к станциям на 30 минут вперёд и публикует их в `queue.v1`; машине, подъезжающей к своей станции, рекомендует станцию с меньшим ожиданием и публикует решение в `decision.v1`. В комплекте — генератор телеметрии с дублями и опозданиями.

- Постановка задачи: [docs/TASK.md](docs/TASK.md).
- Как разделена обработка и почему: [ARCHITECTURE.md](ARCHITECTURE.md).
- Учёт времени: [docs/TIMELOG.md](docs/TIMELOG.md).

Стек: Python 3.11–3.13, confluent-kafka (librdkafka, транзакции), pydantic v2 на границе, Kafka 4.3 (KRaft) в docker compose. Потоковый фреймворк не используется: один процесс, транзакционный цикл consume → process → produce.

## Быстрый старт

Нужны Docker с compose v2 и `make`.

```bash
make up          # собрать образ и поднять стенд: брокер, создание топиков, процессор, генератор
make health      # готовность процессора: ready (партиция назначена, цикл жив)
```

Генератор пишет 40 машин площадки из `config/site.toml` с ускорением ×10, 2 % дублей и 2 % опозданий. Первые решения появляются в течение нескольких секунд после старта (машины, которые уже ближе 1500 м к своей станции).

```bash
make consume-decision   # decision.v1: первые 20 сообщений с начала (read_committed, с ключами)
make consume-queue      # queue.v1: то же
make consume-decision CONSUME_OPTS=                     # поток новых решений, Ctrl+C — выход
make consume-queue CONSUME_OPTS="--from-beginning --max-messages 5 --timeout-ms 10000"
```

Если сообщений меньше 20, чтение заканчивается по 10 с тишины с `TimeoutException` в выводе — это штатно. Пример вывода:

```text
T-15 {"unit_uuid":"T-15","at":"2026-10-07T15:47:44Z","result":"rejected","reason":"no_gain"}
T-06 {"unit_uuid":"T-06","at":"2026-10-07T15:47:44Z","result":"recommended","from_station":"S1","to_station":"S2","gain_seconds":128}
S2 {"station_uuid":"S2","at":"2026-10-07T15:47:44Z","queue":[{"unit_uuid":"T-06","eta":"2026-10-07T15:52:22Z","service_start":"2026-10-07T15:52:22Z","free_at":"2026-10-07T15:56:12Z","wait_seconds":0}]}
```

Прочее: `make logs` (логи стенда), `make ps`, `make topics` (партиции и конфигурация топиков), `make help` (все цели).

```bash
make down        # остановить стенд; данные брокера (топики, снимок, офсеты) сохраняются
make reset       # остановить и удалить данные брокера — с подтверждением
```

После `make down` → `make up` процессор продолжает со своего снимка и закоммиченных офсетов, генератор — с последнего `ts` в топике (иначе ускоренное виртуальное время ушло бы назад, и сообщения отбрасывались бы как нарушающие порядок).

## Локальная разработка

Нужны Python 3.11+ и Poetry 2.

```bash
make install     # зависимости и git-хуки pre-commit
make test        # все тесты без брокера (unit, golden, property)
make check       # ruff, mypy --strict, bandit, gitleaks, тесты с покрытием (порог 90 %)
```

Интеграционные тесты с настоящим брокером:

```bash
make kafka-up    # только брокер и топики (127.0.0.1:9094)
make test-int    # pytest -m integration
make down
```

**Внимание:** `make test-int` останавливает процессор и генератор стенда и **пересоздаёт** топики `telemetry.v1`, `queue.v1`, `decision.v1`, `vqueue.state.v1` — телеметрия, выходы и снимок стенда удаляются.

Процессор и генератор можно запустить и без Docker, против брокера из `make kafka-up`: `make run-processor` (health на :8081, своя группа и `SITE_ID=site-local`) и `make run-generator`. Локальный процессор читает `telemetry.v1` независимо от процессора стенда и хранит свой снимок, но публикует в те же `queue.v1` и `decision.v1`: при поднятом стенде выходы для потребителей дублируются. Параметры генератора: `poetry run python -m vqueue.simulator.generator_main --help` (ускорение, длительность, доли дублей и опозданий, `seed`, вывод в stdout).

CI (GitHub Actions): pre-commit-хуки, тесты на Python 3.11/3.12/3.13, интеграционные тесты с Kafka, сборка образа под amd64/arm64 и smoke-проверка amd64-образа. Публикация образа в ghcr.io — только вручную (Actions → Release → Run workflow на теге `vX.Y.Z`); тег сам по себе ничего не публикует.

## Что сознательно не сделано и почему

- **Метрики (Prometheus) и трассировка.** Для проверки задания достаточно логов и health-check; эндпоинт метрик — отдельный адаптер, домен не затрагивает.
- **Schema Registry, Avro/Protobuf.** ТЗ задаёт JSON; контракт выхода закреплён тестами кодека. Версия схемы — в имени топика (`.v1`).
- **Несколько площадок в одном топике.** Сейчас вход — топик `telemetry.v1` с одной партицией для одной площадки; процессор завершается с ошибкой, если ему назначено больше одной партиции. Вторая площадка — отдельный входной поток и отдельный экземпляр со своими `SITE_ID`, группой и конфигурацией. Модель «площадка = партиция общего топика» потребует `assign()` по сопоставлению `SITE_ID` → партиция вместо `subscribe()`; при одной площадке ТЗ это не нужно.
- **Исполнение рекомендаций генератором.** Обратной связи «сервис → парк» в ТЗ нет: генератор всегда везёт машину к своей станции. Сервис при этом учитывает фактическое положение машины (см. «Принятые решения»).
- **Отдельный процессор приёма** (дедупликация, фазы машины). Граница в коде есть (`domain/ingest.py`, `domain/unit_fsm.py`), вынос — путь эволюции при упоре в CPU; почему не сейчас — ARCHITECTURE.md, п. 7.
- **Dead letter topic.** Некорректное входное сообщение пропускается с предупреждением в логе: повторная обработка не даст другого результата, а потребителя DLQ в задаче нет.
- **Инкрементальный changelog состояния.** Снимок площадки целиком (~11 КБ) пишется раз на батч, а не на сообщение; при таком размере дельты не окупают сложность.
- **Счётчик отброшенных дублей.** Домен не различает «сообщение отброшено» и «ничего не изменилось» — для метрики пришлось бы менять контракт агрегата без потребителя метрики.
- **Безопасность брокера и репликация.** Стенд — один брокер без TLS/SASL, фактор репликации 1, порт открыт только на localhost. Продакшен-настройки — вне объёма задания.
- **Пересечение радиуса разгрузки отрезком траектории** — см. «Известные ограничения».

## Принятые решения

Там, где ТЗ оставляет свободу, приняты следующие решения.

### Геометрия и время

- **Расстояние «по прямой»** — дуга большого круга (haversine) по координатам WGS84, радиус Земли 6 371 000 м.
- **Время в расчётах** — целые секунды epoch. Время в пути `distance / speed` округляется до ближайшей секунды, половина — вверх. Для машины `к разгрузке` округляется сумма путей (до разгрузки и от неё до станции), а не каждый отрезок отдельно.
- **Пороговые сравнения** следуют формулировкам ТЗ: «меньше 50 м», «ближе 1500 м» и «скорость меньше 1 км/ч» — строгие неравенства.
- **«Сейчас»** — наибольший `ts` среди учтённых сообщений всей площадки. Опоздавшее сообщение (с `ts` меньше «сейчас», но новее последнего для своей машины) учитывается, «сейчас» при этом не уменьшается.
- **Конфигурация** (`config/site.toml`) проверяется строго: неизвестные ключи запрещены, чтобы опечатка не подменялась молча значением по умолчанию. Секцию `[rules]` можно опустить — тогда действуют значения из ТЗ.

### Фазы машины

- **Дубли и порядок** фильтруются по машине: учитывается только сообщение с `ts` строго больше последнего учтённого `ts` этой машины.
- **«На станции»** определяется относительно любой станции, в радиусе которой машина остановилась. Если радиусы станций пересекаются, берётся первая станция в порядке конфигурации; в рабочей конфигурации станции разнесены на километры, и это проверяется тестом. Пока машина в радиусе, манёвр со скоростью не ниже порога не меняет фазу.
- **Момент входа в радиус** станции запоминается при первом сообщении внутри радиуса и сохраняется, пока машина из него не выйдет: это «приезд» по правилу 3 для машины, ожидающей занятую станцию. Если первое известное сообщение машины уже внутри радиуса (старт сервиса), моментом входа считается `ts` этого сообщения — реальный вход неизвестен.
- **Выход из радиуса станции** после фазы «на станции» переводит машину в «к разгрузке» — даже если она уехала, не дождавшись обслуживания. Машина, проехавшая радиус станции без остановки, остаётся в фазе «к станции». Машина «к разгрузке» переходит в «к станции» только после выхода из радиуса точки разгрузки, в который она перед этим вошла.

### Занятие станции

- **Занятие станции** происходит по первому сообщению машины в фазе «на станции», пришедшему в момент, когда станция свободна (в момент `free_at` она уже свободна). Поскольку фаза «на станции» сохраняется при манёвре в радиусе, ожидающая машина может занять освободившуюся станцию и сообщением в движении.
- **Повторного занятия** в рамках одного визита нет: машина, отстоявшая 230 с и продолжающая стоять в радиусе, станцию снова не занимает — даже если в промежутке станцию занимала и освободила другая машина. Визит определяется моментом входа в радиус.
- **Досрочное освобождение**: если занявшая машина вышла из радиуса раньше 230 с, станция освобождается в момент первого сообщения вне радиуса.

### Очередь

- **ETA едущей машины** отсчитывается от момента её последней позиции: `last_ts + время в пути`, но не раньше «сейчас». Позиция может быть до 30 с давности, и отсчёт от «сейчас» систематически сдвигал бы приезд на возраст позиции.
- **Ожидающая в радиусе машина** (не занявшая станцию) стоит в очереди с `eta` = моментом входа в радиус; её ожидание отсчитывается от этого момента. Машина, уже отстоявшая своё и ещё не уехавшая, в очередь не попадает. Машина «к разгрузке», проезжающая радиус станции, ожидающей не считается: её приезд считается по пути через разгрузку. Машина «на станции» у другой станции (в том числе отстоявшая там) в очередь своей станции не попадает, пока не уедет. Ожидающая не начинает обслуживание раньше освобождения станции предыдущей машиной, даже если это освобождение уже в прошлом.
- **Равные ETA** упорядочиваются по идентификатору машины (`unit_uuid`) — для детерминированного результата. Границы: позиция ровно 30-секундной давности ещё свежая, приезд ровно на горизонте 30 минут ещё в очереди.
- **Куда едет машина** для расчёта очередей: машина «на станции» относится к станции, где стоит; иначе — к рекомендованной (если рекомендация действует), иначе — к своей. Перенаправление снимается, когда машина уезжает со станции — после обслуживания или не дождавшись его. Машина, проигнорировавшая рекомендацию и вставшая на свою станцию, учитывается там, где фактически стоит.

### Рекомендация

- **Ожидание при выборе станции** считается по готовой очереди станции: момент освобождения — наибольший `free_at` среди машин, приезжающих строго раньше (занявшая станцию — всегда раньше). Сама машина в очереди своей станции на этот расчёт не влияет. Ожидание считается по текущей очереди: освобождение станции, уже наступившее к «сейчас», не учитывается (в очереди его больше нет). При равных ETA «раньше» понимается так же, как в очереди: обслуживание идёт по `(ETA, unit_id)`, поэтому машина с тем же ETA и меньшим идентификатором считается приехавшей раньше — ожидание из решения совпадает с позицией в очереди.
- **Станция за горизонтом** 30 минут в выборе не участвует. Своя станция участвует всегда: решение принимается ближе 1500 м от неё. При равенстве ожиданий: своя станция, затем ближайшая к машине, затем по идентификатору. Выигрыш ровно 60 с — уже рекомендация. Отказ `stale_telemetry` проверяется первым: при несвежем сообщении ожидания не считаются.
- **Решение один раз за заезд**: после расчёта (рекомендации или любого отказа, включая `stale_telemetry`) следующий расчёт для машины возможен только после того, как она побывала на станции. Если первое сообщение машины уже ближе 1500 м к своей станции в фазе «к станции», решение принимается сразу.

### Публикация

- **`queue.v1`**: очереди всех станций пересчитываются на каждое учтённое сообщение (свежесть, горизонт и занятость зависят от общего «сейчас») и публикуются, если изменились записи очереди (состав, порядок или любое время). Поле `at` в сравнении не участвует. Пустые очереди при старте не публикуются. Публикации частые: ETA стоящей вдали от станции машины растёт вместе со «сейчас». Решение публикуется раньше изменений очередей, которые оно вызвало.

### Площадка и генератор

- **Геометрия рабочей площадки** (`config/site.toml`) подобрана под реалистичную неравномерную нагрузку при числах ТЗ (40 машин, 4 станции, 230 с на машину): станции в 11–14 км от разгрузки и в ~2,5 км друг от друга, закрепление 13/10/9/8. Нагрузка станций (машин × 230 с / цикл; цикл — путь туда-обратно на 10 м/с плюс 200 с стоянки) ≈ 1,23 / 0,93 / 0,71 / 0,62 — у перегруженной S1 копится очередь, и рекомендации перебрасывают её машины на соседние станции. При равномерном закреплении и близкой разгрузке все станции перегружены втрое, и рекомендации теряют смысл.
- **Генератор** — отдельное приложение, моделирующее парк: машины едут по прямой с постоянной скоростью, стоят у станции в точке внутри радиуса, обслуживаются 200 с. Из-за манёвра (30 с) ожидающая машина начинает обслуживание не раньше чем через 230 с после начала предыдущей, а сервис по правилу освобождения считает станцию свободной, как только машина вышла из радиуса (~204 с): предсказания сервиса систематически раньше фактического начала обслуживания на ~26 с (см. «Известные ограничения»). Рекомендаций генератор не исполняет — каждая машина всегда едет к своей станции: обратной связи от сервиса к парку в ТЗ нет. Дубли отправляются сразу за оригиналом, опоздания — задержкой отправки старого `ts` на 1–60 с. Прогон детерминирован по `seed`.

## Известные ограничения

- **Предсказания сервиса на данных генератора раньше фактического начала обслуживания на ~26 с** — следствие модели манёвра генератора (см. «Генератор»). Расхождение постоянно и не накапливается по очереди.
- **Машина, проехавшая станцию без стоянки**, после въезда на разгрузку снова едет к своей станции: перенаправление снимается (ТЗ п.4, «следующий заезд снова начинается к своей станции»). Новое решение она получит только после того, как побывает на станции (ТЗ п.5), — в этом заезде расчёта не будет.
- **Переход «к разгрузке» → «к станции»** требует хотя бы одного учтённого сообщения внутри радиуса точки разгрузки (на 36 км/ч это ~10 сообщений). Если все они потеряны или отброшены фильтром порядка, машина останется в фазе «к разгрузке» до прибытия на станцию: её ETA будет завышен на путь через разгрузку, а рекомендация в этом заезде не сработает. Снять ограничение можно проверкой пересечения радиуса отрезком между соседними позициями; при генераторе со случайными опозданиями отдельных сообщений риск пренебрежимо мал.
- **Занятие станции решает порядок обработки сообщений разных машин.** Порядок гарантирован только внутри одной машины (фильтр по `ts`), а сообщения разных машин применяются в порядке поступления, без «откатов». Если сообщение ожидающей машины опоздало и пришло после того, как станцию заняла другая машина, занятие за ней не пересматривается. Инвариант «занятия не перекрываются» при этом сохраняется. Полная детерминированность при повторном прогоне обеспечивается единым порядком сообщений во входном топике (см. [ARCHITECTURE.md](ARCHITECTURE.md)).
- **Один активный экземпляр на площадку, переход на резервный, статическое членство** — см. [ARCHITECTURE.md](ARCHITECTURE.md), п. 4. Два живых экземпляра с одним `INSTANCE_ID` недопустимы — `docker compose up --scale processor=2` не поддерживается.
- **Число партиций существующих топиков** `kafka-init` не меняет (`--if-not-exists`; переприменяются только настройки `vqueue.state.v1`): после изменения схемы топиков нужен `make reset`.
